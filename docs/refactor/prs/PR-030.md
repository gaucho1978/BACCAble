**PR-030 — Powiązanie UDS z rzeczywistym żądaniem CAN**

Typ: **INTEGRATE**. Model: GPT-5.6 Sol / medium. Budżet produkcji: **450 linii**.

Wymagane dokumenty: [kontrakt](../EXECUTION_PL.md), [decyzje](../DECISIONS_PL.md), [akceptacja](../ACCEPTANCE_PL.md).

**Warunki wejścia:** [PR-029](PR-029.md), [PR-016](PR-016.md), [PR-004](PR-004.md). Bez dodatkowej bramki wejściowej; wymagany odbiór sprzętowy opisano poniżej.

**Problem i oczekiwany rezultat.** Bieżąca strona nie decyduje, do jakiego parametru należy odpowiedź.

**Dokładny zakres pracy.**

- C1 scheduler korzysta z uds_reader; zapamiętuje ID/generację przed enqueue, pozostawia zwykły okres wyboru następnego parametru.
- Dodać opcjonalny lokalny token i zdarzenie TX-start do wpisu CAN dla UDS; stary can_tx pozostaje wrapperem bez tokena. Odmowa enqueue nie uruchamia timeoutu odpowiedzi.
- Handler extended przekazuje ramkę readerowi, a wynik aktualizuje cache właściwego ID; unsupported wyświetla brak danych i nie nadaje.

**Poza zakresem.** Diagnostyka sterująca dyno/hamulcami, zmiana innych handlerów i gwarancja odróżnienia identycznego późnego DID.

**Kryteria akceptacji.** Wszystkie warunki wspólne oraz:

- [ ] PR-030-A1: Dwa DID tego samego ECU, odpowiedzi w odwrotnej kolejności → tylko oczekiwany aktualizowany.
- [ ] PR-030-A2: Zmiana strony przy pending nie przypisuje wartości nowej stronie.
- [ ] PR-030-A3: Odrzucone enqueue nie udaje wysłania; przyjęte uruchamia response timer po HAL start.
- [ ] PR-030-A4: Po błędzie/timeout następny cykl może odpytać kolejny parametr; brak floodu i odczytu unsupported.
